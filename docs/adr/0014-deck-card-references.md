# ADR 0014 — A deck references cards by `image_key`, not by the site's id

**Status:** accepted
**Date:** 2026-08-26
**Amends:** [ADR 0006](0006-website.md) Q11's frozen persistence format — the first
amendment to it, and the event it was frozen against
**Closes:** [#83](https://github.com/tskrlabs/hololive-ocg-wiki/issues/83)

## Context

On 2026-08-26 the official card list grew from 2,650 to 2,686 cards. The 36 new hEB01
cards were inserted **mid-sequence**, and 82 existing cards were renumbered to make room:
each kept its `card_number` and its artwork, and was handed a different `?id=`.

Card ids are the official site's own detail-page ids, read straight from `?id=` hrefs
(`scrape/card_list.py`). So the pipeline imported the renumbering faithfully, which is
correct behaviour and is exactly the problem.

`seed` failed 19 batches in with `UNIQUE constraint failed: cards.image_key` — the upsert
keys `ON CONFLICT(id)` while `image_key` carries a unique index (ADR 0009 D6). A D1 batch
is atomic, so nothing was written.

**That crash was luck, and the luck is the point.** The real hazard is silent. Decks are
stored *as card ids*, in `localStorage` and inside shared deck-code URLs. After a seed, a
poisoned id does not fail to resolve — it resolves to the wrong card:

    id 2582  was  hBP01-051_UR_02   ->  now  hEB01-007_SR
    id 2594  was  hBP01-026_SR_02   ->  now  hEB01-019_SR

No error, no gap, nothing to catch. A player opens a saved deck and one card is quietly a
different card. 82 of 2,650 ids, about 3%.

**There is no safe subset.** "Seed only the 36 new cards" fails too: 27 of the 36 land on
ids D1 already uses for other cards. The renumbering is one interlocked shift.

## Decision

**A deck references a card by `image_key`.** The internal numeric `id` stays exactly where
it is.

### Why not make `image_key` the primary key

The obvious reading of #83 was "re-key card identity on `image_key`". It does not survive
the schema. `cards_fts` is an FTS5 virtual table addressed **by numeric rowid**, and
`hEB01/hEB01-004_SR` is not a number. An FTS5 column cannot be indexed for lookup, so
deleting by anything but rowid scans the whole table — about 6M rows read per reseed
(schema.sql). We need both: a numeric key that is fast, and a stable key that is durable.

`image_key` is already the stable one everywhere else. Card URLs are `image_key` verbatim
(D6), the API resolves them that way (`by-key/:set/:stem`), and R2 objects are keyed on it
— which is why the 36 new images published fine during the failed run while the seed
refused.

### `cardRefFormat`, not `APP_VERSION`

The stored shape gains one field:

    cardRefFormat?: "id" | "image-key"    // absent or "" means "id"

`APP_VERSION` is deliberately **not** the migration trigger, even though Q11 stamps it into
every deck. It is one string doing two jobs — app release marker and format marker — and
overloading it means a routine release bump reads as a format change to the migration
predicate. A dedicated field triggers on what actually changed and leaves `APP_VERSION`
free to move.

`decode()` already does `version: parsed.version ?? ""`, so codes carrying an empty version
exist in the wild. Absent and empty both mean `"id"`.

### The mapping is permanent

`pipeline/data/identity/id-to-image-key-20260826.json` captures `id -> image_key` as
production D1 held it **before** the seed: 2,650 rows, 2,650 distinct keys, every key still
present in the 2,686-card build. Nothing was removed, so every old reference resolves
exactly rather than approximately.

It cannot be regenerated by re-running anything — after the seed, the ids no longer mean
what they meant. It is committed against the `pipeline/data/` ignore for that reason.

**The full 2,650-entry map ships, not the 82-entry delta.** The delta is 29× smaller
(2.4 KB vs 71 KB) and repairs the same decks, but it cannot distinguish *unchanged* from
*unknown*: with the delta alone every non-poisoned id looks identical to garbage, so the
shim would have to trust unknown ids and hand them to the API — which is precisely how a
wrong card slips through. The 69 KB buys the property the whole fix rests on. It is static
and immutable, so it caches for a year, and `card-urls.json` is already bundled at 205 KB.

Bundled at build time like `card-urls.json` rather than served from an endpoint: it is
frozen history, and a failed fetch mid-migration would force a choice between blocking the
deck and migrating without the map.

### Migration is silent, eager and backed up

Saved decks migrate at mount, in one pass, with **no confirmation prompt**. The mapping is
lossless, so a prompt would ask the user to approve a fact, and every prompt is a chance to
click the wrong thing on their own saved deck. A dismissible aggregate toast reports the
count for transparency, not approval, and names no cards — after migration the deck holds
exactly the cards it always meant to, and inviting an audit of a provably correct change
spends attention for nothing.

The pre-migration `localStorage` value is copied to
`hololive-ocg-wiki-decks.pre-image-key` before the first write. Eager migration touching
every saved deck at once is the thing worth insuring against.

### Deck codes are translated forever, never rewritten

A shared code arrives from a Discord message pasted at an arbitrary future date. We cannot
rewrite it — it is in someone else's message — so `decode()` inspects `cardRefFormat` and
runs id-form codes through the mapping on the way in. This path has no end date, which is
what makes the mapping permanent rather than a migration artifact to delete later.

### Unresolvable ids keep their slot

An id absent from the full map is genuinely foreign: a hand-edited `localStorage`, a
corrupted paste, or a card withdrawn by a future update. It keeps its slot with a
placeholder and a search-by-card-number picker.

Never dropped silently — a vanished card in a 50-card deck is invisible, and the user is
the only one who knows what was meant. Never refuses the whole deck either: one bad id
should not cost 49 good ones.

### Ordering: the shim ships before the seed

This inverts the obvious order, since the cards are what players are waiting for, and it is
not negotiable. If the seed lands first, decks saved *before* it hold old ids and decks
saved *in the gap* hold new ids — **both stamped `0.9.0`, indistinguishable**. A migration
would then repair the first group and corrupt the second, with no way to tell them apart.

Shipping the shim first has no such window: converting a deck to `image_key` is safe
against either database, because `image_key` did not move and `by-key` already exists.

## Consequences

The 2,686-card set ships the day the shim lands. Once decks no longer reference ids, the
renumbering stops being dangerous and `seed` proceeds normally.

**`seed` keeps its refusal.** The guard added in `d8bd9dd` stays after this ADR is
implemented: it is what makes the *next* renumbering a stop with an explanation rather than
a silent 3% corruption. It reports `renumbered N` beside the source counts, and no flag
clears it — the damage lands outside the database, which is the class D10 says to refuse
rather than gate.

`cardRefFormat` gives the next format change a predicate that already exists.

**What this does not fix:** the pipeline still ingests the site's ids, and D1 still keys on
them. A future renumbering will still trip the seed guard and still need a mapping captured
before it lands. Making the pipeline itself identity-stable is a larger change and is not
attempted here; the deck format is the surface where the damage was silent, and that is the
one this closes.
