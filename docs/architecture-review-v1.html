Problem. Card query has two interfaces, so every consuming view is forked into a legacy copy and an API copy that drift apart.

Solution. One useCardQuery interface; the data source becomes an internal adapter — HTTP in prod, local JSON in dev — and the forked views collapse to one each.

wins
  • leverage: one interface, ~14 call sites
  • locality: query logic in one module
  • two adapters justify the seam
  • delete ~6 forked view files
  • stop importing 8 MB at boot
  • interface is the test surface
The legacy half is already dead — not live-forked. pages/index.vue renders only the API variants; the four legacy views and Filter.vue are unreferenced, and plugins/cards.ts provides a $cardStore nothing reads — while still importing 8 MB (cards_i18n.json) at every boot. This is deletion first, deepening second.

Problem. The filter's shape is written out in three incompatible forms and the empty-filter literal appears five times; filter-states.ts exposes ~25 methods over a thin body.

Solution. Derive the shape from the domain enums; one toApiParams, one createEmpty, and per-field resets collapse into clear(section?).

wins

  • interface shrinks; ~14 resets → one
  • kills the bloom-level mismatch bug
  • toApiParams: one mapping, not three
  • pure module, tested directly
  • drop the legacy reset aliases

Problem. A deck is three arrays, so add / remove / count each fork three ways, and the size rules (1 oshi · 50 main · 20 yell) are re-written inline in the deck page and the floating deck.

Solution. A deep Deck module keyed by section; callers pass a card and the module routes it and enforces the limits behind the interface.

wins
  • locality: bucket rules in one module
  • each op written once, not thrice
  • limits stop leaking into templates
  • leverage: status() reused by both views
  • validation testable through interface
  • new section = one edit

Problem. Three deck-list components each re-derive the same pipeline — count duplicate ids, dedupe, fetch cards, join, resolve image_path — two verbatim and one as a hand-rolled Map variant.

Solution. A deep useDeckCards(cardIds) returning { card, count }[] plus loading; the three components render it and stop deriving.

tackle first

Unify the two card-query stores

It's the root the other duplication grows from — the two interfaces are why Filter, SearchInput, and the three list views each exist twice. Placing the seam inside one useCardQuery module (HTTP adapter in prod, local-JSON adapter in dev) collapses the fork, deletes ~6 view files, and stops the legacy store from importing 8 MB at every boot. The live page already runs the API adapter, so this consolidates toward where the code is going — not away from it.
