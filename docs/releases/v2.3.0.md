# v2.3.0: decks stop trusting a number that moves

A minor release with one subject: the official site reuses its own card ids, and saved
decks were keyed on them. Nothing here was reported by a user, because the failure this
prevents produces no error and no missing card. It hands you a deck you did not build.

## The official list renumbered 82 cards

On 2026-08-26 the card list went from 2,650 to 2,686 cards. The 36 new hEB01 cards were
inserted mid-sequence, and 82 existing cards were pushed along to make room: same card
number, same artwork, new `?id=`.

Card ids come from the site's own `?id=` hrefs, so the pipeline imported the renumbering
faithfully. That is correct behaviour, and it is exactly the problem. Decks are stored as
card ids, in `localStorage` and inside every shared deck-code URL, so after a seed:

```
id 2582  meant  hBP01-051_UR_02   now means  hEB01-007_SR
id 2594  meant  hBP01-026_SR_02   now means  hEB01-019_SR
```

A renumbered id does not fail to resolve. It resolves to the wrong card. Nothing throws,
no slot is empty, and a player opens a saved deck holding cards they never picked.

## The database caught it by accident

`seed` failed 19 batches in with `UNIQUE constraint failed: cards.image_key`. The upsert
keys `ON CONFLICT(id)` while `image_key` carries a unique index, so a card could not take a
key another row still held. D1 batches are atomic, so nothing was written.

That crash was luck, not design. It fired on a mechanical collision that happened to sit in
front of the real hazard, and it is the only reason the corruption never shipped.

## A deck now references `image_key`

`image_key` is the identifier that did not move: it is already the card URL, the API
resolves by it, and R2 objects are keyed on it, which is why the new images published fine
during the run that refused to seed.

The internal numeric id stays where it is. `cards_fts` is an FTS5 table addressed by
numeric rowid, and making `image_key` the primary key would mean either keeping a surrogate
anyway or scanning the whole table per delete.

Saved decks migrate on load, exactly and silently, from a snapshot of `id -> image_key`
captured from production before the seed: 2,650 rows, 2,650 distinct keys, every key still
present in the new build. No card was removed, so every old reference resolves exactly
rather than approximately. The pre-migration state is copied to
`hololive-ocg-wiki-decks.pre-image-key` before anything is written.

There is no confirmation prompt. The mapping is lossless, so a prompt would ask you to
approve a fact, and every prompt is a chance to click the wrong thing on your own deck.

Shared deck codes are translated on decode and never rewritten, because they live in
messages that never expire. That path has no end date, which is what makes the snapshot
permanent rather than a migration artifact to delete later.

The format marker is a new `cardRefFormat` field, deliberately not `APP_VERSION`. That
field is an app release marker, and reusing it would make a routine version bump read as a
format change. Absent and empty both mean the old form.

Recorded as [ADR 0014](../adr/0014-deck-card-references.md), which amends ADR 0006 Q11's
frozen persistence format. The first amendment to it, for the event it was frozen against.

## A card that cannot be resolved keeps its slot

If a reference names no card, the slot stays, with the card number read out of the key and
a link to browse that set. Dropping it silently would make a missing card in a 50-card deck
invisible, and you are the only one who knows what was meant. It can be removed, which
needed its own path: every other deck control picks a section by card type, and a slot with
no card has none.

## `seed` orders its writes now

With decks off the site's ids, the renumbering is no longer dangerous, only awkward. Writes
are ordered so the end of each chain goes first and frees its key. Rehearsed against a local
copy of the real schema loaded with all 2,650 production rows: 2,686 rows and 2,686 distinct
keys, no collision, no deletes.

Two narrower refusals remain, for shapes no ordering can fix: a cycle, where two cards want
each other's key, and a write blocked by a row the run does not rewrite. Neither occurs in
this set.

## Known gaps

**The pipeline still ingests the site's ids, and D1 still keys on them.** A future
renumbering will trip the seed guard again and still needs a mapping captured before it
lands. Making the pipeline itself identity-stable is a larger change and was not attempted;
the deck format is where the damage was silent, and that is what this closes.

**Two bugs in this release shipped past a green `make check`.** An import attribute that
`vue-tsc` and Vitest both accept but the app parser rejects, and a local variable named
`ref` that suppressed its own auto-import. Both were caught by opening the page. Both now
have scans in the test suite, but the underlying gap is real: `make check` runs unit tests,
and only `make check-site` builds. That split is deliberate, to keep the pre-commit hook
fast, and it means neither typecheck nor unit tests can see a class of failure that only
appears in a browser.

**`?set_code=` is still the only filter with a URL.** The unresolved-card link uses it
because there is no `?q=` to link to. Serialising the rest of the filter state remains its
own piece of work.
